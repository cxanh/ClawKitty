# ClawDesk 个人 Agent 助手产品设计方案

## 文档速览

这份文档专门说明：
- 最初从 OpenClaw 原型出发的整体设计
- 桌面端与移动端的初始设想
- 作为历史背景保留的参考内容

最后更新：2026-03-12


## 1. 项目定位

ClawDesk 不再定义为单纯的“OpenClaw 壳 + 设备管理工具”。

新的统一方向是：

`面向大一新生的个人 Agent 助手平台`

它的核心价值不是让用户理解复杂技术细节，而是让用户像在和一个随身助理聊天一样：
- 随时询问 Agent 现在在做什么
- 给 Agent 布置任务
- 查看任务进展和结果
- 清楚知道 Agent 当前能用哪些模型、技能、工具
- 在必要时看到电脑状态与安全审批信息

设备管理、Relay、OpenClaw 兼容层仍然重要，但它们在产品层面是“支撑能力”，不是用户感知的第一主角。

## 2. 目标用户

第一目标用户：
- 刚进大一的新生
- 技术理解有限
- 希望有一个随时可问、能帮忙做事、不会太复杂的个人助手

他们更关心的问题是：
- “我现在该做什么？”
- “你帮我看看作业/课程/日程/资料整理好了没有？”
- “这个 Agent 现在在忙什么？”
- “我能让它帮我做哪些事？”

而不是：
- 端口号是多少
- Browser Relay 具体怎么附着
- Runtime 内部进程如何调度

## 3. 产品核心承诺

ClawDesk 需要始终满足 4 个产品承诺：

### 3.1 对话式
用户应当优先通过聊天完成交互，而不是先学会配置复杂面板。

### 3.2 可见性
用户必须能看清：
- Agent 当前状态
- 当前任务
- 最近做过什么
- 哪一步卡住了
- 是否需要自己确认审批

### 3.3 能力透明
用户需要看得懂：
- 当前可用模型
- 当前可用技能
- 当前可用工具
- 哪些能力可用，哪些能力不可用

### 3.4 对小白友好
所有关键页面都要尽量避免专业术语堆叠。

我们需要更多使用：
- “你可以让 Agent 帮你做这些事”
- “当前 Agent 正在处理中”
- “这里需要你确认一下”

而不是只显示：
- Runtime degraded
- Relay auth rejected
- scope mismatch

## 4. 产品形态

### 4.1 桌面端
桌面端是 Agent 主节点，负责：
- Agent 运行
- 模型与工具接入
- 任务执行
- 审批与安全边界
- 本地资源访问
- Browser Relay 和系统能力桥接

### 4.2 Android 端
Android 端不是只读监控器，而是后续要变成：
- 移动聊天入口
- 移动任务下发入口
- Agent 状态查看入口
- 审批提醒与结果查看入口

第一版可以不全部实现，但规划必须围绕这个方向。

### 4.3 小程序端
小程序端后续定位为：
- 轻量消息入口
- 任务提醒
- 状态速览
- 简单问答与跳转

不承担复杂控制面板职责。

## 5. 核心场景

### 场景 A：随时聊天
用户在电脑或手机上对 Agent 说：
- “帮我整理今天课程相关资料”
- “看看我还有什么待办”
- “把下载目录里的 PDF 按课程分类”
- “总结一下这周我和 Agent 做了什么”

### 场景 B：查看 Agent 在干什么
用户打开 App 后，第一眼就应该看到：
- Agent 是否在线
- 当前正在处理的任务
- 最近完成的任务
- 最近失败的任务
- 是否有等待审批的动作

### 场景 C：理解能力边界
用户需要能直观看到：
- 当前有哪些模型可用
- 当前有哪些技能已启用
- 当前有哪些工具可调用
- 某个任务为什么失败，是模型不可用、技能缺失，还是用户未授权

### 场景 D：手机远程布置任务
用户在手机上对 Agent 说：
- “我回宿舍前，帮我把明天上课资料准备好”
- “看一下电脑上那个任务跑完没有”
- “总结一下今天的学习安排”

这就是后续 Android 端最重要的方向之一。

## 6. 版本策略

## 6.1 v1.0 桌面基础版
目标：先把桌面端做成一个真正能运行的 Agent 主站。

重点：
- 安装型桌面应用
- 首次启动和新手引导
- 桌面聊天入口
- Agent 任务中心
- Agent 活动流
- 模型 / 技能 / 工具概览
- 设备状态与日志作为支撑信息

## 6.2 v1.1 移动伴侣版
目标：让 Android 成为可用的 Agent 陪伴端。

重点：
- Base URL 配置
- 首页状态摘要
- 移动聊天入口
- 移动任务下发
- 配对与审批状态
- 模型 / 技能 / 工具概览只读页

## 6.3 v1.2 个人工作流版
目标：让 Agent 真正承担“个人助理”职责。

重点：
- 任务模板
- 学习场景模板
- 更清晰的审批与执行解释
- 能力推荐
- 更强的任务追踪和历史回顾

## 7. 产品模块重构

新的产品模块建议固定为：

1. `Chat`
- 对话入口
- 多轮消息
- 任务解释
- 当前上下文

2. `Tasks`
- 当前任务
- 待处理任务
- 已完成任务
- 失败任务
- 定时任务与自动化

3. `Activity`
- Agent 最近在做什么
- 哪一步完成了
- 哪一步失败了
- 哪一步需要审批

4. `Capabilities`
- 模型概览
- 技能概览
- 工具概览
- 哪些已启用
- 哪些不可用

5. `Device & Runtime`
- 设备状态
- Relay 状态
- 日志和告警
- 运行健康检查

6. `Pairing & Mobile`
- 移动端配对
- scope 管理
- 审批历史

## 8. 对 OpenClaw 的重新定义

OpenClaw 继续是重要基础，但在整体产品中应被定义为：

`兼容层与运行时能力来源，而不是最终用户理解产品的主视角。`

这意味着：
- 代码层仍复用 OpenClaw 能力
- 兼容已有数据目录和 Browser Relay
- 但产品文案、页面命名、功能组织要围绕 Agent 助手来表达

## 9. 设计原则

### 9.1 默认说人话
不要默认展示底层实现名词。

### 9.2 先解释，再展示细节
用户看到失败时，先看到：
- 发生了什么
- 需要做什么

再看到技术细节。

### 9.3 先任务，后系统
主导航优先展示：
- 聊天
- 任务
- Agent 状态

系统状态页放在次级入口。

### 9.4 所有危险操作都要可见、可审计、可撤销
Agent 可以更聪明，但边界必须更清楚。

## 10. 当前开发方向修正

接下来所有规划和开发都要按以下顺序校正：

1. 先把桌面端收口为个人 Agent 主站
2. 再把 Android 端收口为移动聊天与任务伴侣
3. 设备管理、Relay、配对继续保留，但作为支撑能力
4. 功能设计优先照顾大一新生，而不是高级技术用户

一句话结论：

`ClawDesk 的方向是“个人 Agent 助手”，不是“设备管理面板”。`
